# 用户管理前后端重设计方案

## 1. 背景与目标

当前后台已经具备基础用户管理能力：

- 前端已有 `/system/user` 页面
- 支持用户列表、新增、编辑、绑定角色、绑定职位、启用/禁用、批量启用/禁用
- 后端已有 `/user/list`、`/user/add`、`/user/update`、`/user/roles/update`、`/user/positions/update` 等接口

这说明本次工作不是“从零补一个用户管理模块”，而是一次**围绕 UI/UX 与查询能力的重设计**。现状中的主要问题有：

- 页面视觉层次偏弱，整体更像工具页，缺少成熟后台应有的专业感
- 列表筛选能力过于基础，当前核心查询仍停留在 `nickname` 单字段
- 表格首屏信息密度不够合理，管理员需要进入弹窗后才能确认更多信息
- 前端已经有绑定角色、绑定职位等动作，但列表无法直接体现账号治理状态

本次设计目标已经确认如下：

- 视觉方向采用 `C. 精炼专业式`
- 能力重点优先提升筛选体验
- 筛选重点先做账号维度
- 交互采用“统一搜索框 + 高级筛选面板”
- 改动边界为前后端一起调整

最终目标是把用户管理页升级为一个**视觉更成熟、筛选更顺手、首屏信息更清晰**的企业后台页面，同时尽量复用现有前后端结构，控制实现风险。

## 2. 设计范围

### 2.1 本次要做

- 重构用户管理页面的视觉层次与信息结构
- 将当前基础筛选升级为“统一搜索 + 高级筛选”
- 扩展后端 `/user/list` 查询参数，支持账号维度与治理维度筛选
- 扩展用户列表返回字段，支持首屏展示角色、职位与时间信息
- 优化表格列结构与操作区层次
- 优化新增/编辑用户弹窗的表单分组与确认体验
- 为本次改动补充必要的单元测试与关键路径验证

### 2.2 本次不做

- 新建独立用户详情页
- 新建登录审计专页
- 导出用户列表
- 用户物理删除
- 多列排序体系
- 大面积统计卡或运营驾驶舱布局
- 重写现有角色绑定、职位绑定流程的接口语义

## 3. 现状分析

### 3.1 前端现状

当前前端用户页已经具备基础模块：

- 路由入口：`admin-rsbuild/src/routes/system/user/index.tsx`
- 主列表组件：`admin-rsbuild/src/routes/system/user/#UserTable.tsx`
- 表单组件：`#CreateUserForm.tsx`、`#UpdateUserForm.tsx`
- 绑定组件：`#RoleDrawer.tsx`、`#PositionDrawer.tsx`

当前页面问题主要集中在以下方面：

- 筛选区只支持昵称搜索与租户 ID 输入，无法满足管理员常见的账号检索习惯
- 表格中“账号信息”“角色/职位”“时间信息”分散或缺失，首屏扫读成本高
- 操作区按钮数量较多，视觉主次不够明确
- 页面容器和表格视觉层次偏平，缺少企业后台的精炼感

### 3.2 后端现状

后端 `/user/list` 已存在，但能力较基础：

- 当前请求只支持 `current`、`pageSize`、`ids`、`nickname`、`tenantId`
- 当前返回只包含 `id`、`nickname`、`username`、`tenantId`、`tenantName`、`avatarId`、`isDisable`
- 用户实体本身已经有 `lastLoginTime`，但未在列表响应中暴露

这意味着当前接口已经能够承载列表页，但还不能直接支撑“统一搜索 + 高级筛选 + 首屏摘要展示”的新设计。

## 4. 方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 只做样式美化，不改查询模型 | 实施快，风险低 | 只能解决“更好看”，不能解决“更好用” | 不采用 |
| B | 保留现有页面骨架，升级查询模型、表格结构与视觉层次 | 视觉、效率、信息结构三者平衡；复用现有实现最多 | 需要前后端联动改造 | 采用 |
| C | 改成中枢式用户驾驶舱，加入更多统计与异常提醒 | 视觉冲击强 | 超出当前范围，易偏离精炼后台定位 | 暂不采用 |

本次采用方案 B：**精炼升级型重设计**。

## 5. 总体设计

### 5.1 核心思路

保留现有 `/system/user` 页面入口、`KTable` 表格容器与 `KModal` 表单弹窗体系，不推翻现有用户管理链路，只在其上完成三类升级：

- 查询升级：从“单字段昵称搜索”升级为“统一搜索 + 高级筛选”
- 信息升级：把账号、租户、角色/职位、时间信息在列表首屏中组织清楚
- 视觉升级：把页面做得更克制、更专业、更有层次

### 5.2 视觉定位

采用企业后台的“精炼专业式”风格：

- 主色偏深蓝灰
- 强调色为克制蓝色
- 大面积背景使用浅灰白
- 不使用大块彩色统计区
- 维持高信息密度，但通过间距、字体层级、边框与轻量标签建立秩序感

### 5.3 设计原则

- 默认态尽量简洁，不把所有筛选项一次性摊开
- 高级能力通过折叠面板承载，而不是让页面首屏变重
- 首屏尽量让管理员“一眼看清账号是谁、属于谁、当前状态如何”
- 不为追求视觉效果牺牲操作效率

## 6. 页面结构设计

### 6.1 页面分区

用户管理页拆成 4 个稳定区域：

#### 顶部标题区

- 左侧：页面标题与一句说明文案
- 右侧：`新增用户`、`批量操作`
- 不引入大型指标卡，保持精炼

#### 主筛选区

- 默认只展示一个统一搜索框
- placeholder 为：`搜索用户名 / 昵称 / 用户 ID`
- 右侧放 `高级筛选` 按钮

#### 高级筛选展开区

- 默认收起
- 展开后分组展示条件
- 优先呈现账号维度：
  - 用户名
  - 昵称
  - 用户 ID
- 次级补充治理维度：
  - 租户
  - 状态
  - 是否已绑定角色
  - 是否已绑定职位
- 底部提供 `应用筛选` 与 `重置`

#### 列表区

- 保持 `KTable` 为主承载容器
- 用新的列组织方式提升扫读效率

### 6.2 表格列设计

建议表格列调整为：

- `账号信息`
  - 头像
  - 昵称
  - 用户名
  - 用户 ID
- `默认租户`
- `角色 / 职位摘要`
- `状态`
- `最近登录 / 更新时间`
- `操作`

其中：

- `账号信息` 为主视觉列，承担主要识别任务
- `角色 / 职位摘要` 用两行弱层级文本或轻量标签展示
- `最近登录 / 更新时间` 用双行时间展示，便于判断活跃度与最近维护时间

### 6.3 操作区设计

当前操作按钮较多，本次做收敛处理：

- 主操作保留 `编辑`
- 次级入口使用 `更多`
- `更多` 内放：
  - 绑定角色
  - 绑定职位
  - 启用 / 禁用

这样可以减少一行按钮堆叠，强化操作层级，也更符合精炼专业式风格。

## 7. 查询模型设计

### 7.1 请求参数升级

保留原有分页字段，并把 `/user/list` 请求模型升级为以下结构：

| 参数 | 含义 | 说明 |
|---|---|---|
| `current` | 当前页码 | 保留 |
| `pageSize` | 每页条数 | 保留 |
| `ids` | 用户 ID 列表 | 保留，供已有场景复用 |
| `keyword` | 统一搜索关键字 | 新增 |
| `username` | 用户名筛选 | 新增 |
| `nickname` | 昵称筛选 | 保留并扩展使用场景 |
| `userId` | 单个用户 ID | 新增 |
| `tenantId` | 租户筛选 | 保留 |
| `isDisable` | 启用 / 禁用状态 | 新增 |
| `hasRole` | 是否已绑定角色 | 新增 |
| `hasPosition` | 是否已绑定职位 | 新增 |

### 7.2 统一搜索规则

统一搜索框绑定 `keyword`，规则如下：

- 当输入为纯数字时：
  - 优先匹配 `id`
- 当输入为文本时：
  - 同时匹配 `username`
  - 同时匹配 `nickname`

这样可以满足管理员最常见的三种查找习惯：

- 按工号式用户 ID 查
- 按登录用户名查
- 按展示昵称查

### 7.3 高级筛选规则

高级筛选面板中：

- `username`、`nickname` 支持独立输入
- `userId` 做精确匹配
- `tenantId` 走租户选项选择
- `isDisable` 用全部 / 启用 / 禁用
- `hasRole`、`hasPosition` 用是 / 否 / 不限

### 7.4 前端交互规则

- 页面首次进入：
  - 统一搜索框可见
  - 高级筛选默认收起
- 提交统一搜索：
  - 重置分页到第一页
  - 触发列表查询
- 点击 `高级筛选`：
  - 展开或收起面板
  - 不丢失当前统一搜索值
- 点击 `应用筛选`：
  - 合并高级筛选条件并触发查询
  - 重置分页到第一页
- 点击 `重置`：
  - 清空统一搜索与高级筛选全部条件
  - 恢复默认列表

## 8. 列表返回模型设计

### 8.1 返回字段扩展

建议 `UserListItemVo` 在现有基础上新增：

| 字段 | 含义 |
|---|---|
| `roleNames` | 角色名称列表 |
| `positionNames` | 职位名称列表 |
| `lastLoginTime` | 最近登录时间 |
| `updatedAt` | 最近更新时间 |
| `hasRole` | 是否已绑定角色 |
| `hasPosition` | 是否已绑定职位 |

### 8.2 前端展示规则

- `roleNames`、`positionNames`
  - 默认只展示前 1 到 2 项
  - 超出时显示 `+N`
  - 为空时显示弱提示文案，如“未绑定角色”
- `lastLoginTime`
  - 显示真实时间
  - 为空时显示“暂无登录记录”
- `updatedAt`
  - 显示最近维护时间

### 8.3 聚合策略

角色与职位摘要应在后端列表查询时一次性聚合并返回，避免前端逐行追加查询，导致：

- 首屏列表闪烁
- 网络请求数量过多
- 行渲染时序不可控

## 9. 前端实现边界设计

### 9.1 页面职责拆分

为了避免单文件继续膨胀，建议在现有 `system/user` 目录下做更细的页面内拆分：

```text
admin-rsbuild/src/routes/system/user/
├── index.tsx
├── #UserTable.tsx
├── #UserToolbar.tsx
├── #UserAdvancedFilter.tsx
├── #UserInfoCell.tsx
├── #UserActionMenu.tsx
├── #CreateUserForm.tsx
├── #UpdateUserForm.tsx
├── #RoleDrawer.tsx
├── #PositionDrawer.tsx
└── #tenantHelper.ts
```

职责建议：

- `index.tsx`
  - 页面容器
- `#UserTable.tsx`
  - 列表查询、分页、列定义装配
- `#UserToolbar.tsx`
  - 统一搜索、按钮区、高级筛选触发
- `#UserAdvancedFilter.tsx`
  - 展开筛选面板
- `#UserInfoCell.tsx`
  - 账号信息单元格
- `#UserActionMenu.tsx`
  - 行内主操作与更多菜单

### 9.2 新增与编辑表单

本次不推翻现有表单链路，只做体验升级：

#### 新增用户

- 分组为：
  - 基础信息：昵称、用户名、默认租户
  - 账号设置：密码模式、初始密码、启用状态
- 保留成功后展示“账号 + 初始密码”确认面板的设计
- 优化排版，让其更像结果确认，而不是表单残留页

#### 编辑用户

- 保持单页弹窗
- 分组为：
  - 基础信息
  - 安全设置
  - 状态设置
- 密码字段继续保留“留空表示不修改”的语义
- 可在底部展示最近登录时间作为只读辅助信息

## 10. 后端实现边界设计

### 10.1 控制器层

继续沿用 `/user/list` 作为唯一列表入口，不新开平行接口。这样可以：

- 减少前后端分叉
- 保持 OpenAPI 文档收敛
- 降低已有调用方迁移成本

### 10.2 服务层

`UserService.getList(...)` 需要承担以下职责：

- 解析统一搜索语义
- 解析高级筛选条件
- 进行分页查询
- 聚合租户名称
- 聚合角色名称与职位名称
- 组装最近登录时间与更新时间
- 输出前端所需布尔摘要字段

### 10.3 查询实现原则

- 优先保证正确性，而不是一次性追求复杂查询技巧
- 当前页面仍以列表浏览为主，不引入过度分析型查询模型
- 如果角色/职位关系聚合需要额外查询，优先采用“批量聚合后映射”的方式，避免 N+1

## 11. 错误处理与降级策略

### 11.1 查询参数错误

- 非法页码、页大小、非法 `userId` 等参数，沿用当前校验链路返回标准错误
- 前端继续走现有请求错误提示机制

### 11.2 无结果场景

- 查询结果为空时使用页面空态，不弹错误
- 空态文案按是否存在筛选条件区分：
  - 有条件：`未找到符合条件的用户`
  - 无条件：`暂无用户数据`

### 11.3 摘要字段聚合异常

- 角色/职位摘要聚合失败不应拖垮用户列表主查询
- 更稳妥的降级方式是返回空列表并保持主列表可用

### 11.4 租户映射异常

- 如果租户已删除或映射不存在，沿用现有语义输出“租户已删除”或等价兜底文案

## 13. 交付范围与阶段结论

### 13.1 本次交付范围

- 用户管理页 UI/UX 重设计
- 用户列表查询模型升级
- 首屏信息字段升级
- 高级筛选能力
- 前后端联调
- 必要测试与关键路径验证

### 13.2 阶段结论

本次设计采用“精炼升级型重设计”路线：

- 页面不改成仪表盘
- 视觉采用成熟企业后台风格
- 筛选采用“统一搜索 + 高级筛选”
- 后端在现有 `/user/list` 基础上扩参数和返回字段
- 前端继续复用 `KTable`、`KModal`、现有表单与绑定弹窗体系

这一路线能在控制范围的前提下，同时提升视觉体验、筛选效率与列表信息质量，是当前仓库中性价比最高的实现方式。
