# 设备库存管理设计

## 1. 目标与结论

### 1.1 目标
- 为当前多租户系统新增“设备库存管理”业务域。
- 第一版覆盖设备单件资产的全生命周期管理。
- 支持入库登记、领用、归还、调拨、盘点、报废六类核心动作。
- 前后端均沿用仓库现有分层、命名与权限接入模式，补充必要测试。

### 1.2 已确认结论
- 管理对象是设备 / 资产库存，不是商品或物料。
- 第一版范围是全生命周期，但只包含入库登记、领用、归还、调拨、盘点、报废。
- 资产按单件管理，一物一档，不做批量数量台账。
- 设备台账字段采用以下最小集合：
  - 设备名称
  - 设备分类
  - 资产编号
  - SN / 序列号
  - 所属租户
  - 当前状态
  - 存放位置
  - 当前使用人
  - 购置日期
  - 备注
- 当前使用人绑定现有系统用户。
- 存放位置采用结构化位置数据，不用自由文本。
- 第一版所有业务动作直接生效，不引入审批流。
- 业务域采用独立模块方案，不挂到 `mod-system` 下。

## 2. 范围与非目标

### 2.1 本次范围
- 后端新增独立资产库存业务模块。
- 前端新增资产库存菜单、路由页面与相关 API 模块。
- 新增设备台账、位置管理、盘点任务三类页面。
- 新增设备生命周期动作接口与统一流水留痕。
- 新增数据库表、菜单、权限资源初始化脚本。
- 为关键状态机、前端交互与 API 参数组装补充必要单元测试。

### 2.2 非目标
- 不做移动端布局兼容。
- 不做审批流、单据审核、驳回、撤销等流程态。
- 不做维修保养、保修到期提醒、告警中心、统计报表。
- 不做批量导入导出。
- 不做条码 / 扫码盘点、RFID、打印标签等硬件集成。
- 不引入新的外部依赖。

## 3. 现状摘要

### 3.1 前端现状
- `admin-rsbuild` 使用 TanStack Router 文件路由，路径入口采用“目录 + `index.tsx`”模式。
- 列表页普遍使用项目封装的 `KTable`，弹窗业务容器优先使用 `KModal` / `KDrawer`。
- 权限资源与菜单路径强相关，页面新增通常需要同步补充：
  - 路由页面
  - `permission.ts`
  - `resourceApiProfile.generated.ts`
  - 权限快捷资源映射
- 现有业务页示例可以参考 `src/routes/project/task-type/`。

### 3.2 后端现状
- 后端为 Spring Boot 多模块 Maven 工程，业务域按 `mod-*` 拆分。
- 控制器普遍使用独立 `Controller + Service + Request + Vo + Mapper + domain` 风格。
- API 风格通常使用：
  - `GET /xxx/list`
  - `GET /xxx/detail`
  - `POST /xxx/create`
  - `POST /xxx/edit`
  - 动作接口单独拆路由
- 数据库迁移采用 Flyway 脚本，菜单和权限资源通过 SQL 初始化。
- 系统已有租户、用户、角色、菜单、Casbin 资源权限模型。

### 3.3 当前痛点
- 现有仓库没有库存 / 资产业务域，设备台账与流转无处承载。
- 如果把资产管理塞进 `mod-system`，长期会把业务域和系统配置域混杂。
- 如果不把流转动作抽为独立接口，后续加审批或审计会导致编辑接口语义混乱。

## 4. 方案对比与最终选择

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A | 新增独立资产库存业务模块 | 业务边界清晰，便于后续扩展盘点、报表、审批流 | 初次接入改动面较大 | 采用 |
| B | 挂到 `mod-system` 下作为系统子功能 | 接入快，复用现有系统页模式 | 业务域与系统域混杂，后续维护成本高 | 不采用 |
| C | 只做设备台账与流水，盘点先弱化 | 上线更快，风险更低 | 与已确认的“第一版包含盘点”不一致 | 不采用 |

### 4.1 最终方案
- 采用方案 A，新增独立资产库存业务域。
- 第一版聚焦设备单件资产，不扩展其他库存对象。
- 设备台账、位置管理、盘点任务统一纳入资产库存模块。
- 流程动作直接生效，通过状态机与流水保证一致性。

## 5. 业务域与模块划分

### 5.1 后端模块建议
- `modelDesign/mod-asset/mod-asset-api`
- `modelDesign/mod-asset/mod-asset-biz`

模块职责：
- `mod-asset-api`
  - 对外共享 DTO / 基础接口定义
  - 供其他业务域在需要时引用资产基础类型
- `mod-asset-biz`
  - 资产领域实体、Mapper、Service、Controller
  - 盘点任务、位置树、台账查询与动作流转

### 5.2 前端路由建议
- `/asset/device`：设备台账页
- `/asset/location`：位置管理页
- `/asset/stocktake`：盘点任务页

### 5.3 选择原因
- 设备库存已经是独立业务域，不适合继续放在系统配置模块下。
- 第一版虽然不含维修和报表，但数据模型已经要承载完整生命周期。
- 先独立模块，可以避免后续二次拆分带来的迁移成本。

## 7. 状态机与业务规则

### 7.1 设备主状态
第一版只保留 4 个主状态：
- `IN_STOCK`：在库
- `IN_USE`：领用中
- `LOST`：盘亏 / 未找到
- `SCRAPPED`：已报废

这样设计的原因：
- 第一版不做审批和维修，没必要引入大量中间态。
- 先控制状态数量，能减少接口冲突和前端按钮判断复杂度。

### 7.2 状态流转
- 入库登记：新建设备，状态设为 `IN_STOCK`
- 领用：`IN_STOCK -> IN_USE`
- 归还：`IN_USE -> IN_STOCK`
- 调拨：
  - 在库设备允许调整位置，状态保持 `IN_STOCK`
  - 领用设备允许调整归属位置或使用人，状态保持 `IN_USE`
- 盘点：
  - 信息一致时状态不变
  - 信息不一致时允许校正台账并写入盘点流水
  - 未盘到时可标记为 `LOST`
- 报废：
  - `IN_STOCK` 或 `LOST` 可报废
  - `IN_USE` 默认不允许直接报废，必须先归还

### 7.3 第一版强约束
- 领用时必须指定系统用户。
- 在库设备必须有位置。
- 领用中的设备必须有当前使用人。
- 报废后设备不可再领用、归还、调拨。
- 盘点校正会更新台账当前值，但原盘点明细与流水必须保留。
- 所有动作都记录操作人、操作时间、备注。

## 9. 接口设计

### 9.1 设备台账接口
- `GET /asset/device/list`
  - 分页查询设备台账
- `GET /asset/device/detail`
  - 查询设备详情
- `POST /asset/device/create`
  - 入库登记
- `POST /asset/device/edit`
  - 编辑台账基础信息
- `POST /asset/device/receive`
  - 领用
- `POST /asset/device/return`
  - 归还
- `POST /asset/device/transfer`
  - 调拨
- `POST /asset/device/scrap`
  - 报废

设计原则：
- 动作型接口与编辑接口分离，避免语义混杂。
- 后续如果追加审批流，只需扩动作接口与状态，不必推翻台账 CRUD。

### 9.2 分类接口
- `GET /asset/category/list`
- `POST /asset/category/create`
- `POST /asset/category/edit`

说明：
- 第一版前端未必单独出分类管理页，但后端建议先具备基础能力。

### 9.3 位置接口
- `GET /asset/location/list`
- `POST /asset/location/create`
- `POST /asset/location/edit`

### 9.4 盘点接口
- `GET /asset/stocktake/list`
- `GET /asset/stocktake/detail`
- `POST /asset/stocktake/create`
- `POST /asset/stocktake/check`
- `POST /asset/stocktake/complete`

其中：
- `create`：按范围生成任务与待盘点明细
- `check`：提交单条或批量盘点结果
- `complete`：结束任务并汇总差异结果

### 9.5 辅助下拉接口
- `GET /asset/options/users`
- `GET /asset/options/locations`
- `GET /asset/options/categories`

这样做的原因：
- 前端页面不需要直接拼多个业务域接口。
- 可以在资产域内部做统一格式裁剪，降低页面耦合。

## 10. 关键业务流程

### 10.1 入库登记
- 前端提交台账信息。
- 后端校验租户、分类、位置合法性。
- 校验资产编号唯一。
- 创建设备台账，默认状态为 `IN_STOCK`。
- 写入一条 `INBOUND` 流水。
- 返回设备详情。

### 10.2 领用
- 校验设备状态必须为 `IN_STOCK`。
- 校验领用用户存在且属于当前租户。
- 更新设备状态为 `IN_USE`。
- 更新当前使用人与最近操作时间。
- 记录领用流水。

### 10.3 归还
- 校验设备状态必须为 `IN_USE`。
- 更新状态为 `IN_STOCK`。
- 清空当前使用人。
- 更新归还后所在位置。
- 记录归还流水。

### 10.4 调拨
- 允许在库设备调整位置。
- 允许领用设备调整归属位置或使用人。
- 状态保持不变。
- 记录前后差异流水。

### 10.5 盘点
- 创建任务时按范围快照设备集合。
- 盘点过程中逐条提交结果。
- 差异项允许现场校正。
- 完成任务时汇总未盘到设备，必要时标记为 `LOST`。

### 10.6 报废
- 校验设备状态允许报废。
- 更新状态为 `SCRAPPED`。
- 记录报废时间与备注。
- 写入报废流水。

## 11. 异常处理与并发控制

### 11.1 通用校验失败
- 资产编号重复。
- 分类不存在或已停用。
- 位置不存在或已停用。
- 用户不存在。
- 设备不属于当前租户。

### 11.2 状态冲突
- 非在库设备不能领用。
- 非领用中设备不能归还。
- 已报废设备不能再调拨、领用、归还。
- 已完成盘点任务不能继续提交明细。

### 11.3 并发保护
第一版至少要防止同一设备被重复操作。

建议做法：
- 设备状态变更 SQL 带当前状态作为更新条件。
- 更新结果为 0 时返回“设备状态已变化，请刷新后重试”。
- 关键动作使用事务包裹“更新台账 + 写流水”。

### 12.1 菜单建议
- 顶级菜单：`/asset`
- 子菜单：
  - `/asset/device`
  - `/asset/location`
  - `/asset/stocktake`

### 12.2 权限资源建议
页面级菜单资源：
- `/asset/device`
- `/asset/location`
- `/asset/stocktake`

动作级按钮资源建议：
- `/asset/device/manage`
- `/asset/device/receive`
- `/asset/device/return`
- `/asset/device/transfer`
- `/asset/device/scrap`
- `/asset/location/manage`
- `/asset/stocktake/manage`

说明：
- 资源命名需与前端路径和按钮显隐逻辑保持一致。
- 同步补充资源到权限快捷资源映射，避免角色分配时漏掉接口依赖。

### 12.3 多租户约束
- 所有台账、位置、分类、盘点任务、流水均带 `tenantId`。
- 所有列表、详情、动作接口都必须从当前登录租户上下文中读取租户，不接受前端随意指定其他租户。
- 用户与位置等关联校验必须限制在当前租户范围内。

## 13. 测试方案

### 13.1 后端测试
执行入口按仓库约定从 `modelDesign/boot` 模块触发。

建议至少覆盖：
- 入库成功
- 资产编号重复失败
- 在库领用成功
- 非在库领用失败
- 领用后归还成功
- 已报废设备不能归还 / 调拨
- 盘点完成后不能继续提交
- 多租户下不能读取其他租户设备

优先层级：
- Service 层测试
- 状态机与事务边界测试
- 少量 Controller 层参数校验测试

### 13.2 前端测试
建议至少覆盖：
- 设备台账页筛选参数组装
- 行级操作按钮随状态变化的显隐判断
- 领用 / 归还 / 报废表单提交参数
- 盘点提交结果的状态映射
- API 模块请求参数与响应类型约束

### 13.3 手工验证闭环
至少验证以下主路径：
- 入库 -> 领用 -> 归还
- 入库 -> 调拨
- 入库 -> 发起盘点 -> 校正位置
- 入库 -> 报废
- 多租户隔离下不可见其他租户设备

## 14. 发布、回滚与风险

### 14.1 发布影响
- 新增后端模块与相关依赖。
- 新增数据库表与 Flyway 脚本。
- 新增菜单、权限资源、Casbin 授权初始化脚本。
- 新增前端页面、API 模块与权限常量。

### 14.2 主要风险
- 菜单与权限资源漏配，导致页面不可见或接口被拦截。
- 多租户过滤遗漏，导致跨租户数据污染。
- 状态机并发保护不足，导致同一设备被重复领用。
- 盘点完成与现场变更并发时，可能覆盖最新台账。

### 14.3 回滚策略
- 代码层可直接回滚版本。
- 数据层采用“保留表结构、关闭入口”的回滚思路，不做破坏性删除。
- 若上线初期发现流程问题，可先通过菜单和权限收口，避免继续写入错误业务数据。

## 15. 实施建议拆分

建议按以下顺序落地：
1. 后端基础表与领域模型
2. 设备台账与动作接口
3. 位置管理
4. 盘点任务与明细
5. 菜单、权限、前端页面
6. 前后端测试与回归验证

这样拆分的原因：
- 先把核心台账和状态机打稳，页面开发才有稳定接口基础。
- 盘点依赖台账与位置模型，适合放在后续阶段。
- 菜单和权限应在业务接口趋稳后再集中接入，减少反复调整初始化脚本。

## 16. 结论

本次设计确定新增独立“设备库存管理”业务域，围绕设备单件资产的一物一档模型展开，采用结构化位置、系统用户绑定、精简状态机、统一流水、任务式盘点的方案落地。

第一版不引入审批流、不扩展维修与报表，但已经为后续继续扩展生命周期能力保留了清晰的数据边界和接口演进空间。
