# 登录审计字段增强设计

## 1. 背景与目标

当前系统已经具备基础登录历史能力：

- 后端在用户名密码登录成功后写入 `userLoginHistory`
- 前端个人中心“安全设置”页签展示最近登录历史
- 当前字段仅包含登录流水号、登录 IP、登录方式、登录时间

这套能力能够满足最基础的“最近登录记录”展示，但还不足以支撑以下场景：

- 用户自助识别“这是不是我自己的设备和浏览器”
- 管理员排查异常登录、暴力尝试、错误密码等安全事件
- 后续扩展企业微信等其它登录方式时，统一记录登录审计信息

本次设计目标是在**尽量复用现有登录历史链路**的前提下，把现有能力升级为“登录审计事件记录”，同时兼顾两类使用场景：

- 用户侧：在个人中心查看最近成功登录设备信息
- 管理侧：后续提供登录审计查询能力，支持成功/失败登录排查

## 2. 设计范围

### 2.1 本次要做

- 扩展现有登录历史数据模型，使其可承载登录审计字段
- 成功登录与失败登录均记录审计事件
- 记录原始 `User-Agent` 以及解析后的浏览器、操作系统、设备类型
- 为失败登录增加结果状态与失败原因码
- 增强当前登录历史接口返回字段
- 增强个人中心“最近登录历史”展示信息
- 预留管理员侧登录审计查询接口的数据模型与筛选方向

### 2.2 本次不做

- IP 归属地解析
- 风险评分、异常设备识别、风控规则引擎
- 设备指纹或浏览器指纹
- 登录后全链路行为审计
- 新建独立安全审计平台

## 3. 现状分析

### 3.1 当前后端链路

- `AuthService.passwordLogin(...)` 在账号密码校验通过后构造 `CurrentAdmin`
- `UserLoginHistoryService.recordPasswordLogin(...)` 仅在成功登录后记录历史
- `UserLoginHistory` 当前字段较少，只适合“登录历史”展示，不足以支撑完整审计
- `LoginHistoryVo` 当前只对前端暴露 4 个字段

### 3.2 当前前端链路

- 个人中心安全页签通过 `/passport/login_history` 获取最近登录记录
- 当前列表展示字段仅为登录时间、登录方式、登录 IP、登录流水号
- 页面结构已经存在，适合在现有列表上补充设备化信息，不需要重做交互容器

### 3.3 关键问题

- 当前只记录成功登录，失败尝试完全缺失
- 当前没有 `User-Agent` 原文，无法支持后续安全排查
- 当前无法识别浏览器、操作系统、设备类型
- 当前没有统一的登录结果状态字段，无法区分“成功事件”与“失败事件”

## 4. 方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 现有表仅追加少量展示字段 | 改动最小 | 很快会演变成语义混乱的半审计表 | 不采用 |
| B | 继续沿用现有表与服务链路，但按“登录审计事件表”扩展字段和写入逻辑 | 复用现有实现最多，能平滑支持成功/失败登录、个人中心展示、管理员查询预留 | 表名和类名短期仍叫“登录历史”，语义不够完美 | 采用 |
| C | 新建独立登录审计表，现有历史表只保留给用户展示 | 模型最干净 | 第一版改动范围明显变大，交付节奏变慢 | 暂不采用 |

## 5. 总体设计

### 5.1 核心思路

采用方案 B：**复用现有 `userLoginHistory` 这条链路，但将其升级为“登录审计事件记录表”使用**。

短期内保留现有类名与表名，避免为了命名纯洁度把第一版范围扩大为大迁移。语义调整通过字段模型和服务职责完成：

- 用户侧“最近登录历史”只读取成功登录记录
- 审计侧记录成功与失败全部事件
- 同一套底层数据同时支撑用户自助查看与管理员后续审计

### 5.2 领域边界

本次只覆盖“登录事件本身”的审计增强，不扩大到其它安全事件：

- 包含：登录成功、登录失败
- 不包含：登出、改密、权限变更、关键页面访问

### 5.3 查询边界

- 当前用户最近登录历史：只返回成功登录事件
- 管理员登录审计查询：后续可基于同一张表扩展，支持成功/失败混合筛选

## 6. 数据模型设计

### 6.1 现有表升级原则

保留现有字段：

- `userId`
- `tenantId`
- `loginId`
- `loginIp`
- `loginType`
- `createTime`

新增字段建议如下：

| 字段 | 类型建议 | 说明 | 是否必需 |
|---|---|---|---|
| `loginStatus` | `varchar(32)` | 登录结果：`SUCCESS` / `FAILURE` | 必需 |
| `username` | `varchar(128)` | 本次尝试使用的登录账号 | 必需 |
| `userAgent` | `text` 或较长字符串 | 原始浏览器 UA | 必需 |
| `browserName` | `varchar(64)` | 浏览器名称，如 Chrome、Edge | 必需 |
| `browserVersion` | `varchar(64)` | 浏览器版本 | 建议 |
| `osName` | `varchar(64)` | 操作系统名称，如 Windows、macOS | 必需 |
| `osVersion` | `varchar(64)` | 操作系统版本 | 建议 |
| `deviceType` | `varchar(32)` | 设备类型：`DESKTOP / MOBILE / TABLET / UNKNOWN` | 必需 |
| `failureReasonCode` | `varchar(64)` | 失败原因码 | 失败场景必需 |
| `failureReasonText` | `varchar(255)` | 内部排障说明 | 建议 |

### 6.2 字段语义说明

#### `username`

- 成功登录时记录当前成功登录用户的用户名
- 失败登录时记录请求里提交的用户名
- 即使最终找不到用户，也应保留本次尝试的输入账号，便于管理员审计

#### `userId`

- 成功登录时必填
- 失败登录时，如果已经定位到用户，可记录该用户 ID
- 失败原因是“用户不存在”时允许为空

#### `tenantId`

- 成功登录时必填
- 失败登录时，如果已识别到用户且能确定租户，则记录
- 无法识别时允许为空

#### `loginId`

- 成功登录时使用当前登录会话流水号
- 失败登录时为空

#### `userAgent`

- 原始请求头完整保留
- 用作审计取证与后续规则升级依据
- 不建议只存解析后的浏览器名称，否则后续无法补充分析逻辑

#### `failureReasonText`

- 仅用于内部审计排查
- 不直接回显到登录页对外错误提示
- 保持安全边界，避免向攻击者暴露过多细节

### 6.3 枚举建议

#### 登录状态枚举

| 枚举值 | 含义 |
|---|---|
| `SUCCESS` | 登录成功 |
| `FAILURE` | 登录失败 |

#### 登录方式枚举

第一版保留并扩展现有值：

| 枚举值 | 含义 |
|---|---|
| `PASSWORD` | 用户名密码登录 |
| `QYWORK` | 企业微信登录或绑定后续可复用 |

第一版实际仍只写入 `PASSWORD`，但模型为未来扩展预留。

#### 设备类型枚举

| 枚举值 | 含义 |
|---|---|
| `DESKTOP` | 桌面端 |
| `MOBILE` | 手机 |
| `TABLET` | 平板 |
| `UNKNOWN` | 未识别 |

#### 失败原因码枚举

| 枚举值 | 含义 |
|---|---|
| `USER_NOT_FOUND` | 用户不存在 |
| `PASSWORD_MISMATCH` | 密码错误 |
| `USER_DISABLED` | 用户已禁用 |
| `USER_TENANT_MISSING` | 用户未绑定租户 |
| `TENANT_DISABLED` | 租户不可登录 |
| `SYSTEM_ERROR` | 系统异常或未分类异常 |

这些原因码用于审计与统计，不改变当前登录接口对外错误文案策略。

## 7. 写入链路设计

### 7.1 成功登录写入

当前成功登录写入链路继续保留，但改造为统一调用“登录审计记录”方法。

推荐逻辑：

1. 接收到登录请求，读取用户名、客户端 IP、`User-Agent`
2. 完成账号密码校验与租户校验
3. 构造成功登录会话 `CurrentAdmin`
4. 保存会话
5. 更新用户最后登录 IP、最后登录时间
6. 写入成功登录审计事件

成功事件应包含：

- `loginStatus = SUCCESS`
- `username`
- `userId`
- `tenantId`
- `loginId`
- `loginIp`
- `loginType = PASSWORD`
- `userAgent`
- `browserName`
- `browserVersion`
- `osName`
- `osVersion`
- `deviceType`

### 7.2 失败登录写入

失败登录记录需要覆盖主要失败分支：

1. 用户不存在
2. 用户已禁用
3. 密码错误
4. 用户未绑定租户
5. 租户不可登录
6. 其它系统异常

推荐逻辑：

1. 请求一进入服务层，先解析 `username`、`loginIp`、`userAgent`
2. 在每个失败分支抛出业务异常前，先记录失败审计事件
3. 再继续抛出当前对外业务异常，保持接口表现不变

失败事件应包含：

- `loginStatus = FAILURE`
- `username`
- `userId`：能识别则写，不能识别为空
- `tenantId`：能识别则写，不能识别为空
- `loginId = null`
- `loginIp`
- `loginType = PASSWORD`
- `userAgent`
- `browserName`
- `browserVersion`
- `osName`
- `osVersion`
- `deviceType`
- `failureReasonCode`
- `failureReasonText`

### 7.3 UA 解析责任

建议在后端统一解析，不把浏览器识别逻辑放到前端。原因如下：

- 审计记录必须以服务端接收到的请求为准
- 前端解析不可信，容易被伪造或与服务端记录不一致
- 后续管理员查询、统计分析都依赖服务端落库结果

服务端可增加独立的小型解析组件，例如“登录客户端信息解析器”，职责仅为：

- 输入：原始 `User-Agent`
- 输出：浏览器名称/版本、操作系统名称/版本、设备类型

该组件保持单一职责，便于单元测试与未来替换实现。

## 8. 接口设计

### 8.1 当前用户最近登录历史接口

当前接口继续沿用：

- `GET /passport/login_history`

返回语义调整为：

- 默认只返回当前用户最近成功登录记录
- 仍按时间倒序返回最近 10 条

返回字段建议扩展：

| 字段 | 说明 |
|---|---|
| `loginId` | 登录流水号 |
| `loginIp` | 登录 IP |
| `loginType` | 登录方式 |
| `loginTime` | 登录时间 |
| `browserName` | 浏览器名称 |
| `browserVersion` | 浏览器版本 |
| `osName` | 操作系统名称 |
| `osVersion` | 操作系统版本 |
| `deviceType` | 设备类型 |

不建议在当前用户最近登录历史接口中直接暴露：

- `userAgent`
- `failureReasonCode`
- `failureReasonText`

原因是这类字段更偏管理员审计与内部排障，不适合直接展示给普通用户。

### 8.2 管理员登录审计查询接口预留

第一版建议至少在后端设计层面明确未来接口方向：

- `GET /auth/login_audit/page`

建议支持的筛选条件：

- 用户名
- 租户 ID
- 登录状态
- 登录方式
- 登录 IP
- 浏览器名称
- 操作系统名称
- 设备类型
- 时间范围

建议返回字段：

- 基础事件字段
- `userAgent`
- `failureReasonCode`
- `failureReasonText`

第一版可以先不做完整前端页面，但后端模型和服务设计要按这个方向抽象，避免后续返工。

## 9. 前端展示设计

### 9.1 个人中心安全页签

当前“最近登录历史”表格在现有结构上补充设备信息即可，不需要重做页面。

建议展示列调整为：

| 列名 | 说明 |
|---|---|
| 登录时间 | 保留 |
| 登录方式 | 保留 |
| 登录 IP | 保留 |
| 浏览器 | 新增，展示“名称 + 版本” |
| 操作系统 | 新增，展示“名称 + 版本” |
| 设备类型 | 新增，展示中文文案 |
| 登录流水号 | 保留 |

展示建议：

- 浏览器列：优先展示 `browserName`，有版本则拼接版本
- 操作系统列：优先展示 `osName`，有版本则拼接版本
- 设备类型映射为中文，如桌面端、手机、平板、未知
- 保持当前“只展示成功记录”的用户认知，不混入失败尝试

### 9.2 管理员视图

本次先不强制落完整页面，但推荐后续做成独立列表页，而不是塞进个人中心。

原因：

- 管理员关注的是检索、筛选、追踪
- 普通用户关注的是“最近是否有陌生设备登录”
- 两类页面目标不同，不适合共用同一视图模型

## 10. 错误处理与安全边界

### 10.1 对外错误口径

登录接口当前对外错误文案保持现有策略，不因审计增强而改变：

- 不向终端用户暴露过细的失败原因
- 避免被攻击者利用错误信息做账号探测

### 10.2 审计写入失败策略

建议采用以下策略：

- 登录主流程优先级高于审计记录
- 成功登录后，如果审计写入失败，应记录服务端日志，但不影响本次登录成功响应
- 失败登录场景下，如果审计写入失败，也不覆盖原有业务异常结果

这样可以避免“审计功能故障导致整套登录不可用”。

### 10.3 敏感字段控制

- `userAgent` 仅用于后台审计或内部排障，不在普通用户接口直接返回
- `failureReasonText` 不直接回显前端登录页
- 后续管理员接口应受权限控制，不允许普通用户读取其它人的登录审计数据

## 11. 测试与验证设计

### 11.1 后端单元测试

建议新增以下测试：

- UA 解析组件：
  - Chrome / Edge / Safari / 企业微信内浏览器等典型 UA 解析正确
  - 解析失败时回退为 `UNKNOWN`
- 登录审计记录组装：
  - 成功登录事件字段完整
  - 用户不存在时失败事件字段正确
  - 密码错误时失败事件字段正确
  - 用户禁用、租户异常时失败事件字段正确

### 11.2 后端集成验证

建议验证以下关键路径：

1. 正确账号密码登录成功，审计表写入成功事件
2. 错误密码登录失败，审计表写入失败事件
3. 不存在账号登录失败，审计表写入失败事件
4. 个人中心登录历史接口只返回成功事件

### 11.3 前端验证

建议补充：

- 类型定义与接口字段同步
- 安全页签列表新增列渲染测试
- 浏览器/操作系统/设备类型空值与未知值兜底展示

## 12. 实施建议

### 12.1 推荐拆分顺序

1. 扩展后端领域模型与返回对象
2. 增加 UA 解析组件与枚举
3. 改造登录成功/失败写入逻辑
4. 增强最近登录历史查询，仅返回成功事件
5. 增强前端类型与个人中心表格展示
6. 补充单元测试与关键路径验证

### 12.2 数据库迁移建议

本次属于数据表扩字段改造，需提供安全迁移脚本：

- 新增字段尽量允许空值作为过渡
- 旧数据允许解析字段为空，不强制回填
- 新逻辑上线后，新增记录逐步带齐完整字段

如后续确认该表将长期承担审计职责，再考虑在第二阶段进行类名、表名和索引的正式清理。

## 13. 验收标准

满足以下条件即可认为第一版达标：

1. 成功与失败登录都会产生审计记录
2. 审计记录包含原始 UA、浏览器、操作系统、设备类型、登录结果
3. 失败登录带有明确失败原因码
4. 当前用户最近登录历史接口仍可正常使用，且仅返回成功记录
5. 个人中心可展示最近成功登录的浏览器、操作系统、设备信息
6. 现有登录接口对外行为与错误口径不发生非预期变化

## 14. 风险与后续演进

### 14.1 当前风险

- 现有表名和类名仍偏“登录历史”语义，和审计职责存在轻微偏差
- UA 解析依赖规则或第三方库，需注意选择稳定实现
- 失败登录写入点分散在多个失败分支，改造时要避免漏记

### 14.2 后续演进建议

- 第二阶段可补充管理员审计列表页
- 第三阶段可接入 IP 归属地与简单异常提醒
- 如果登录方式继续扩展，再考虑把当前表正式升级命名为登录审计表
