# 任务详情抽屉快捷添加子任务设计

## 1. 目标与结论

### 1.1 目标
- 在现有任务详情抽屉中增加“快捷添加子任务”能力。
- 让用户在父任务上下文中连续录入子任务，而不被频繁打断。
- 保持现有完整任务表单的价值，把“快捷创建”和“完整补录”组合起来，而不是做两套完全独立流程。

### 1.2 已确认结论
- 入口范围采用 `2B`：主入口只放在任务详情抽屉里，任务列表和看板本次不扩散。
- 交互形态采用 `1C`：既支持标题级快捷创建，也支持创建后继续补全详情。
- 创建成功后的默认行为采用 `3A`：留在当前父任务抽屉里，只刷新子任务列表，不自动跳走。
- 抽屉布局采用 `B`：从 `概览 / 变更日志` 扩展为 `概览 / 子任务 / 变更日志`，子任务放在独立标签页，不塞回概览页。
- 子任务列表首版采用 `4A`：每条子任务只保留“补充详情”一个动作，不提供“查看详情”第二入口。
- 子任务负责人默认继承父任务负责人。

## 2. 范围与非目标

### 2.1 本次范围
- 扩展任务详情抽屉标签页结构，新增“子任务”页签。
- 在“子任务”页签顶部提供标题级快捷创建能力。
- 在“子任务”页签中展示当前父任务的子任务列表与进度摘要。
- 支持对子任务打开现有完整任务表单进行补充编辑。
- 补齐前端任务模型和接口封装，使 `parentTaskId`、子任务列表查询等能力真正可用。

### 2.2 非目标
- 不在任务列表页、敏捷看板卡片、“我的待办”等其他页面新增快捷子任务入口。
- 不做多级子任务。
- 不在子任务列表里直接修改状态、负责人、优先级或排期。
- 不引入子任务树形视图、任务树表格、甘特图或依赖图。
- 不新增复杂的多层嵌套详情抽屉流。

## 3. 现状摘要

### 3.1 已有后端能力
- 后端 `ProjectTaskEditRequest` 已包含 `parentTaskId` 字段，说明任务父子关系的模型已预留。
- 后端 `ProjectTaskDetailVo` 已包含 `parentTaskId`、`parentTaskTitle`、`childTaskCount`、`completedChildTaskCount` 等字段，说明父任务详情侧已具备展示子任务摘要的基础。
- 仓库中已有 [任务关系设计文档](/Users/wanz/web/wwwroot/modelDesign/docs/superpowers/specs/2026-04-03-task-relations-design.md)，其中已经明确：
  - 只支持一级子任务
  - 父任务在所有子任务完成后自动完成
  - 子任务本质上仍然是普通任务，只是挂了 `parentTaskId`

### 3.2 已有前端能力
- 任务详情抽屉组件位于 [#TaskPreviewDrawer.tsx](/Users/wanz/web/wwwroot/modelDesign/admin-rsbuild/src/routes/agile-board/#TaskPreviewDrawer.tsx)，当前只有 `概览 / 变更日志` 两个页签。
- 抽屉底部已有明确定位：“侧栏用于快速查看与流转任务，完整字段编辑仍通过任务表单完成。”
- 完整任务表单位于 [#TaskCreateForm.tsx](/Users/wanz/web/wwwroot/modelDesign/admin-rsbuild/src/routes/project/components/#TaskCreateForm.tsx)，当前支持新建与编辑，但前端提交参数尚未把 `parentTaskId` 真正接上。
- 打开完整任务表单统一通过 [taskModalService.tsx](/Users/wanz/web/wwwroot/modelDesign/admin-rsbuild/src/service/taskModalService.tsx) 的 `openTaskModal` 完成。

### 3.3 当前痛点
- 虽然领域模型已经支持子任务概念，但任务详情抽屉还没有为“父任务下连续录入子任务”提供顺手入口。
- 当前若要创建子任务，用户只能退回完整任务创建流程，增加上下文切换成本。
- 现有任务表单没有把父任务关系当作默认值链路接通，导致“创建子任务”还停留在设计层。

## 4. 方案对比

| 方案 | 说明 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 在“概览”页中内嵌子任务区 | 抽屉打开即能看到快捷输入和子任务列表 | 录入路径最短，无需切页签 | 概览页会迅速变长，和任务说明争夺首屏空间 | 不采用 |
| B. 新增独立“子任务”页签 | 把快捷创建和子任务列表集中到单独页签 | 信息结构清晰，后续扩展最自然 | 录入前需要多点一次页签 | 采用 |
| C. 头部极简输入 + 其他信息留在概览 | 在摘要区塞入一行快捷输入框 | 看起来最“快捷” | 会挤压现有状态流转与操作区，破坏头部层级 | 不采用 |

最终采用方案 B。

## 5. 最终交互设计

### 5.1 抽屉整体结构
- 任务详情抽屉页签从：
  - `概览`
  - `变更日志`
- 调整为：
  - `概览`
  - `子任务`
  - `变更日志`

设计原则：
- `概览` 继续承担任务进度、排期与任务说明展示。
- `子任务` 单独承担“快捷录入 + 子任务管理入口”的职责。
- `变更日志` 保持不变。

### 5.2 子任务页签结构
子任务页签拆成上下两块：

1. 顶部“快捷创建区”
- 一个单行输入框，placeholder 建议为“输入子任务标题后回车创建”
- 一个“添加”按钮，和回车行为一致
- 一行辅助说明，提示“默认继承父任务负责人，可创建后继续补充详情”
- 创建中时输入框和按钮进入 `loading / disabled`

2. 下方“子任务列表区”
- 顶部展示进度摘要，例如“已完成 2 / 5”
- 列表按常规列表流展示当前父任务下的全部一级子任务
- 每条子任务展示以下最小必要信息：
  - 标题
  - 状态
  - 负责人
  - 更新时间
- 每条子任务首版只保留一个动作：`补充详情`

### 5.3 主流程
1. 用户打开父任务详情抽屉。
2. 切换到“子任务”页签。
3. 输入子任务标题并按回车，或点击“添加”按钮。
4. 前端调用任务创建接口，以当前任务作为 `parentTaskId` 创建子任务。
5. 创建成功后：
   - 输入框清空
   - 子任务列表刷新
   - 父任务详情刷新
   - 用户仍停留在当前父任务抽屉，不发生页面或抽屉跳转
6. 若用户需要补负责人、排期、描述等信息，可点击该子任务的“补充详情”。
7. “补充详情”打开现有完整任务表单，关闭后回到父任务抽屉并刷新相关数据。

### 5.4 为什么首版只保留“补充详情”
- 它最贴合“快捷创建后继续补全信息”的目标。
- 可以避免用户在父任务抽屉和子任务抽屉之间来回跳转而迷路。
- 能让首版把复杂度集中在“顺手创建”和“数据同步”上，而不是做成一个小型多入口管理面板。

## 6. 默认值规则

### 6.1 快捷创建提交的最小字段
快捷创建子任务时，前端提交参数建议至少包含：

```ts
{
  projectId: parentTask.projectId,
  parentTaskId: parentTask.id,
  title: quickInputTitle,
  assigneeId: parentTask.assigneeId,
  priority: parentTask.priority,
  status: defaultTodoStatus,
}
```

### 6.2 默认值来源规则
- `projectId`：直接继承父任务所属项目
- `parentTaskId`：直接写入当前父任务 ID
- `title`：来自快捷输入框
- `assigneeId`：默认继承父任务负责人
- `priority`：默认继承父任务优先级
- `status`：默认取当前任务体系的起始状态
- `description`：默认空
- `workDays`：默认空
- `startTime / dueTime`：默认空

### 6.3 这样设计的原因
- 负责人继承是已确认需求，能显著减少补录动作。
- 优先级继承通常和父任务语义一致，能让子任务默认排序和紧急程度更合理。
- 排期、工时、描述若默认继承，反而容易制造错误数据，所以首版保持空值更稳妥。

## 7. 前端设计

### 7.1 组件落点
- 任务详情抽屉主组件继续在 [#TaskPreviewDrawer.tsx](/Users/wanz/web/wwwroot/modelDesign/admin-rsbuild/src/routes/agile-board/#TaskPreviewDrawer.tsx)
- 可新增子组件以控制复杂度，例如：
  - `#TaskSubtaskPanel.tsx`
  - `#TaskSubtaskQuickCreate.tsx`
  - `#TaskSubtaskList.tsx`

这样做的原因：
- 当前抽屉已经承担概览和变更日志展示，再把子任务区直接堆进去会让文件继续膨胀。
- 子任务页签天然可以独立成一个清晰边界的面板组件，后面如果要在其他地方复用也更方便。

### 7.2 类型定义调整
前端任务类型文件 [project-task.types.ts](/Users/wanz/web/wwwroot/modelDesign/admin-rsbuild/src/api/modules/project-task.types.ts) 建议补齐：
- `CreateProjectTaskParams.parentTaskId?: number`
- `EditProjectTaskParams.parentTaskId?: number`
- `ProjectTaskDetail.parentTaskId?: number`
- `ProjectTaskDetail.parentTaskTitle?: string`
- `ProjectTaskDetail.childTaskCount?: number`
- `ProjectTaskDetail.completedChildTaskCount?: number`

同时建议新增一个更轻量的子任务列表类型，例如：

```ts
interface ProjectTaskChildItem {
  id: number;
  title: string;
  status: string;
  assigneeId?: number;
  assignee?: string;
  updatedAt?: string;
}
```

### 7.3 数据流
1. 父任务抽屉继续通过 `ApiProjectTask.getDetail(taskId)` 获取详情。
2. 切到“子任务”页签时，再单独请求“按父任务查询子任务列表”接口。
3. 创建成功后，统一触发：
   - 当前父任务详情刷新
   - 当前父任务子任务列表刷新
   - 任务列表缓存失效
   - 看板缓存失效
   - 我的待办缓存失效
4. 点击“补充详情”时，继续复用 `openTaskModal` 打开完整任务表单。

### 7.4 为什么子任务列表建议独立接口
- 比把全部子任务塞进详情接口更清晰。
- 后续如果要支持分页、排序、筛选或字段扩展，不需要反复膨胀详情接口。
- 前端能更明确地控制页签内加载状态和局部刷新。

## 8. 后端设计

### 8.1 已有能力接通
后端创建与编辑任务的请求对象已经具备 `parentTaskId` 字段，本次重点不是发明新模型，而是把这条链路真正接通：
- 前端创建任务时允许提交 `parentTaskId`
- 任务保存逻辑继续复用现有子任务校验规则

### 8.2 新增查询接口建议
建议新增按父任务查询子任务列表接口，例如：

```http
GET /projectTask/children?parentTaskId=123
```

返回项首版建议覆盖页面实际展示需求：
- `id`
- `title`
- `status`
- `assigneeId`
- `assignee`
- `updatedAt`

如果后端已有更标准的命名方式，可按现有 Controller 风格落地，但语义应保持“按父任务查询子任务列表”明确可读。

### 8.3 校验规则
需继续沿用并补足以下校验：
- 父任务必须存在
- 父任务必须属于当前项目
- 若父任务本身已经是子任务，则禁止继续创建下一级子任务
- 标题不能为空

### 8.4 负责人为空时的处理
- 若父任务没有负责人，快捷创建仍允许成功
- 此时子任务负责人保持空，不把“负责人继承”变成创建门槛

这样设计的原因：
- “默认继承负责人”是便利规则，而不是强校验规则
- 不能因为父任务数据不完整，就阻断子任务录入流程

## 9. 异常与反馈设计

### 9.1 前端拦截
- 标题为空：直接在输入区提示，不发请求
- 标题只有空白字符：自动 `trim` 后校验为空

### 9.2 接口异常提示
- 父任务已失效或无权限：提示“父任务已失效，请刷新后重试”
- 父任务不可再创建子任务：提示“当前任务已是子任务，不能继续添加下一级子任务”
- 通用创建失败：提示后端返回的可读错误，未提供时使用统一兜底提示

### 9.3 创建成功但刷新失败
- 先给出“子任务创建成功”反馈
- 若随后列表刷新失败，再补提示“列表刷新失败，请手动刷新”

这样做可以避免把“创建成功”误报成“创建失败”，减少用户认知混乱。

## 10. 实施边界与演进方向

### 10.1 本次实施边界
- 只在任务详情抽屉中增加主入口
- 只支持一级子任务
- 只支持标题级快捷创建
- 只支持通过完整任务表单进行补充编辑

### 10.2 后续可演进项
- 子任务列表中的快速状态切换
- 子任务列表中的负责人快捷改派
- 在任务列表 / 看板中增加“添加子任务”入口
- 子任务列表增加分页、排序、折叠策略
- 父任务抽屉中补充“查看子任务详情”能力

本次不实现这些能力，但当前结构不会阻碍未来扩展。

## 11. 风险与控制策略

### 11.1 主要风险
- 子任务页签请求链路补齐后，如果缓存失效不完整，容易出现抽屉内和列表外状态不一致。
- 若直接把大量逻辑写回 `#TaskPreviewDrawer.tsx`，组件复杂度会继续升高。
- 若默认值规则定义不清，可能出现负责人继承、优先级继承和状态默认值不一致的问题。

### 11.2 控制策略
- 明确以“父任务详情刷新 + 子任务列表刷新 + 外部列表缓存失效”作为成功后的统一同步动作。
- 把子任务页签拆成独立面板组件，避免抽屉主文件继续膨胀。
- 将快捷创建默认值集中在一处构造，避免在多个按钮和表单入口重复拼装。

## 12. 验证策略

### 12.1 前端关键路径验证
- 在父任务抽屉的“子任务”页签中输入标题并回车，可以成功创建子任务。
- 点击“添加”按钮与回车行为一致。
- 创建成功后留在当前父任务抽屉，不发生跳转。
- 创建成功后，输入框清空，便于继续录入下一条。
- 子任务列表与父任务进度摘要同步刷新。

### 12.2 默认值验证
- 新建子任务默认带上父任务负责人。
- 新建子任务默认带上父任务优先级。
- 新建子任务默认使用任务体系起始状态。
- 父任务负责人为空时，子任务仍能成功创建，只是负责人为空。

### 12.3 边界与异常验证
- 父任务本身是子任务时，不能继续创建下一级子任务。
- 标题为空或只有空白字符时，前端阻止提交。
- 创建成功但刷新失败时，提示语义准确。

### 12.4 补充编辑验证
- 点击某条子任务的“补充详情”后，能打开完整任务表单。
- 在完整任务表单中保存成功后，返回父任务抽屉，子任务列表和父任务摘要同步刷新。

## 13. 验收标准

- 任务详情抽屉已经存在 `子任务` 独立页签。
- 用户可以在该页签中通过标题输入框快速创建子任务。
- 快捷创建的子任务默认继承父任务负责人和优先级，并绑定 `parentTaskId`。
- 创建成功后用户仍留在父任务抽屉中，可连续录入多条子任务。
- 子任务列表首版只提供“补充详情”动作，且可以正常打开完整任务表单。
- 子任务创建与编辑后，抽屉内外相关任务数据保持同步。
