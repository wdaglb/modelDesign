# 登录审计日志 90 天清理设计

## 1. 背景与目标

当前系统已经具备登录审计能力：

- 登录成功与失败都会写入 `userLoginHistory`
- 当前用户可查看最近成功登录历史
- 管理端已具备登录审计分页查询接口

随着日志持续增长，`userLoginHistory` 会不断累积历史审计数据。若长期不清理，会带来以下问题：

- 表数据持续膨胀，查询与索引维护成本上升
- 审计日志超过业务实际保留期后仍长期占用存储
- 多租户场景下分页查询、筛选和索引命中效果逐渐变差

本次设计目标是在**不引入通用日志治理平台**的前提下，仅针对登录审计日志 `userLoginHistory` 增加“保留 90 天”的清理能力，同时兼顾：

- 手动清理：平台管理员可全局清理，租户管理员可清理本租户
- 自动清理：系统每日定时执行一次全局清理
- 多租户边界清晰，不允许租户越权清理其它租户日志

## 2. 设计范围

### 2.1 本次要做

- 为登录审计日志增加手动清理接口
- 为登录审计日志增加每日定时清理任务
- 将保留天数与定时表达式做成配置项
- 支持平台管理员全局清理
- 支持租户管理员清理本租户日志
- 输出明确的清理结果：删除数量、截止时间、作用范围
- 补充必要的权限校验与测试

### 2.2 本次不做

- 不扩展到任务变更日志、系统消息日志等其它日志表
- 不抽象成通用日志保留框架
- 不增加“清理历史任务表”
- 不做前端管理页面
- 不做日志归档，仅做删除

## 3. 已确认输入

本次与用户确认后的约束如下：

| 项目 | 结论 |
|---|---|
| 清理对象 | `userLoginHistory` |
| 触发方式 | 手动接口 + 定时任务 |
| 权限范围 | 平台可全局，租户管理员仅可清本租户 |
| 权限口径 | 第一版先按角色编码 `super` / `tenant` |
| 默认保留期 | 90 天 |

## 4. 方案对比

| 方案 | 描述 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A | 固定 90 天，手动接口和定时任务都写死 | 改动最小 | 保留策略变化需改代码发版 | 不采用 |
| B | 只针对 `userLoginHistory`，但把保留天数与调度时间配置化；手动和定时共用同一套清理服务 | 聚焦当前需求；可维护性更好；避免过度抽象 | 比 A 多少量配置代码 | 采用 |
| C | 抽象成通用日志清理框架，供多个模块日志复用 | 扩展性最好 | 明显超出当前范围，复杂度偏高 | 暂不采用 |

## 5. 总体设计

### 5.1 核心思路

采用方案 B：**仅针对登录审计日志 `userLoginHistory` 增加专用清理能力，但保留天数与调度表达式可配置**。

实现分三层：

1. 清理服务层：负责实际删除逻辑
2. 手动接口层：负责权限校验、范围控制与结果返回
3. 定时任务层：每日触发一次全局清理

### 5.2 范围模型

第一版支持两种清理范围：

| 范围 | 含义 |
|---|---|
| `GLOBAL` | 清理全库 90 天前登录审计日志 |
| `TENANT` | 清理指定租户 90 天前登录审计日志 |

### 5.3 触发模型

| 触发类型 | 说明 |
|---|---|
| `MANUAL` | 人工调用接口触发 |
| `SCHEDULED` | 系统定时任务触发 |

两者最终都调用同一套底层清理服务。

## 6. 配置设计

建议在现有 `AuthProperties` 下新增以下配置：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `model-design.auth.login-audit.retention-days` | `90` | 登录审计保留天数 |
| `model-design.auth.login-audit.cleanup-cron` | `0 30 3 * * *` | 每日定时清理 cron |

说明：

- `retention-days` 用于手动清理默认值与定时清理固定值
- `cleanup-cron` 控制定时任务执行时间
- 第一版不开放租户管理员自定义保留天数，租户侧统一走系统默认值

## 7. 服务设计

### 7.1 新增服务

建议新增 `LoginAuditCleanupService`，职责仅为：

- 校验保留天数是否合法
- 计算清理截止时间
- 执行全局或租户范围删除
- 返回清理结果对象

### 7.2 服务接口建议

建议提供如下方法：

1. `cleanupGlobal(Integer retentionDays, CleanupTriggerType triggerType)`
2. `cleanupByTenant(Long tenantId, Integer retentionDays, CleanupTriggerType triggerType)`

内部统一收口到私有方法：

`cleanup(Long tenantId, Integer retentionDays, LoginAuditCleanupScope scope, CleanupTriggerType triggerType)`

### 7.3 删除规则

统一删除条件：

- `createTime < cutoffTime`
- 若为租户范围，再增加 `tenantId = ?`

其中：

`cutoffTime = now - retentionDays`

第一版不做“按自然日对齐到凌晨 00:00:00”的复杂规则，直接按当前时间回退保留天数。

### 7.4 删除方式

建议直接通过 MyBatis-Plus 删除，不先查后删：

- 全局：按 `createTime` 条件删除
- 租户：按 `tenantId + createTime` 条件删除

这样实现简单、性能稳定，也更适合大量历史数据清理。

## 8. 手动接口设计

### 8.1 接口路径

建议新增到现有登录审计控制器中：

- `POST /login_audit/cleanup`

控制器仍放在 `LoginAuditController` 下，语义最统一。

### 8.2 请求对象

建议新增 `LoginAuditCleanupRequest`，字段如下：

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `scope` | `String` | 是 | `GLOBAL` / `TENANT` |
| `tenantId` | `Long` | `scope=TENANT` 时必填 | 租户 ID |
| `retentionDays` | `Integer` | 否 | 手动清理保留天数；不传用配置默认值 |

建议第一版加入服务端校验：

- `scope` 非法时报错
- `retentionDays <= 0` 报错
- `scope = TENANT` 且 `tenantId` 为空时报错

### 8.3 返回对象

建议新增 `LoginAuditCleanupResultVo`，字段如下：

| 字段 | 类型 | 说明 |
|---|---|---|
| `deletedCount` | `Long` | 实际删除数量 |
| `scope` | `String` | 本次清理范围 |
| `tenantId` | `Long` | 租户 ID，全局清理为空 |
| `retentionDays` | `Integer` | 实际保留天数 |
| `cutoffTime` | `LocalDateTime` 或格式化字符串 | 删除截止时间 |
| `triggerType` | `String` | `MANUAL` / `SCHEDULED` |

### 8.4 权限边界

第一版按已确认角色编码处理：

| 角色 | 可执行范围 |
|---|---|
| `super` | `GLOBAL`、`TENANT` |
| `tenant` | 仅 `TENANT`，且只能清自己租户 |

服务端校验规则建议如下：

1. 当前用户拥有 `super` 角色：
   - 可全局清理
   - 可按任意租户清理

2. 当前用户拥有 `tenant` 角色：
   - 不允许 `GLOBAL`
   - `scope = TENANT` 时，`tenantId` 必须等于当前登录租户

3. 其它角色：
   - 不允许调用清理接口

说明：

- 第一版这里直接基于现有权限服务的角色编码判断
- 若后续角色编码有正式规范，可再替换为统一常量

## 9. 定时任务设计

### 9.1 调度方式

建议新增专用调度器：

- `LoginAuditCleanupScheduler`

### 9.2 调度频率

默认 cron：

- `0 30 3 * * *`

即每天凌晨 03:30 执行一次全局清理。

### 9.3 调度行为

定时任务固定使用：

- `scope = GLOBAL`
- `retentionDays = 配置默认值`
- `triggerType = SCHEDULED`

定时任务不走 HTTP 接口，不做权限判断，直接调用清理服务。

### 9.4 调度启用

当前 `mod-auth` 模块没有自己的 `@EnableScheduling` 配置，而 `mod-system` 中已有单独调度配置。

为避免隐式依赖其它模块，建议在 `mod-auth` 新增一个认证模块调度配置，例如：

- `AuthSchedulingConfiguration`

在该配置类上添加：

- `@Configuration`
- `@EnableScheduling`

这样登录审计清理任务是否生效，由认证模块自身负责。

## 10. 安全与异常策略

### 10.1 幂等性

清理接口天然幂等：

- 同一时刻重复执行，第一次删除后，后续删除数量会逐步变为 0

### 10.2 主流程隔离

清理失败不会影响登录主流程，因为它是独立入口和独立调度任务。

### 10.3 异常处理

建议统一抛业务异常：

- 非法 `scope`
- 非法 `retentionDays`
- 租户为空
- 越权执行

### 10.4 运行日志

第一版不新增数据库“清理任务表”，只记录应用日志，至少包含：

- 触发方式
- 作用范围
- `tenantId`
- 保留天数
- 截止时间
- 删除数量
- 异常信息

## 11. 测试设计

### 11.1 服务层测试

建议新增测试覆盖：

1. 全局清理时，按 `createTime < cutoffTime` 删除
2. 租户清理时，仅删除指定租户
3. `retentionDays <= 0` 拒绝
4. `scope = TENANT` 且 `tenantId` 为空时报错

### 11.2 权限测试

建议覆盖：

1. `super` 可执行全局清理
2. `super` 可执行指定租户清理
3. `tenant` 不允许执行全局清理
4. `tenant` 只能清理当前租户
5. 非 `super/tenant` 角色拒绝

### 11.3 调度测试

建议覆盖：

1. 定时任务调用全局清理
2. 使用默认保留天数
3. 调度失败时记录错误日志，不抛出阻断应用启动的异常

### 11.4 控制器测试

建议覆盖：

1. 合法请求返回 `deletedCount`
2. 非法 `scope` 返回参数错误
3. 越权租户范围返回错误

## 12. 验收标准

满足以下条件即可视为第一版达标：

1. 可通过手动接口清理 90 天前登录审计日志
2. 平台管理员可全局清理
3. 租户管理员仅可清理本租户
4. 每日定时全局清理可运行
5. 清理结果包含删除数量与截止时间
6. 不影响现有登录审计写入与查询
7. 多租户边界清晰，不允许串租删除

## 13. 风险与后续演进

### 13.1 当前风险

- 第一版角色口径临时采用 `super / tenant`，若正式编码不同需同步调整
- 当前只做应用日志记录，未形成清理历史台账
- 若未来日志量继续增长，后续可考虑进一步引入分区表或归档机制

### 13.2 后续演进建议

- 第二阶段可增加前端管理页
- 第三阶段可扩展到其它日志表
- 后续如有审计合规要求，可增加“归档后删除”而非直接删除
