# 任务子任务、后续任务与标签设计说明

## 1. 背景

当前项目任务能力已经具备以下基础：

- 后端在 `modelDesign/mod-project/mod-project-biz` 中提供了任务的创建、编辑、删除、列表、详情、变更日志、任务成员等能力
- 任务当前是扁平结构，尚未支持父子关系、任务依赖关系和多标签挂载
- 系统已经具备可复用的系统消息能力，可用于任务条件满足后的负责人通知
- 当前 `project` 模型尚未显式保存 `tenantId`，而本仓库的多租户隔离规则要求后续新增能力按租户维度隔离

本次目标是在不把任务模块升级成复杂流程引擎的前提下，为现有任务体系补充三类能力：

- 子任务：任务下挂的一级子任务
- 后续任务：由用户手动创建，并声明依赖若干前置任务；只有前置任务全部完成后，后续任务才能开始，同时通知负责人
- 任务标签：基于租户内共享标签库，为每个任务挂载多个标签

## 2. 已确认需求

### 2.1 子任务规则

- 子任务只是任务下的一个子任务，不做无限层级
- 子任务本质上仍然是一条普通任务，只是挂在父任务下面
- 父任务在所有子任务完成后自动完成
- 父任务有未完成子任务时，不允许手动改成完成状态

### 2.2 后续任务规则

- 后续任务不是系统自动生成，而是用户手动创建
- 创建后续任务时即可关联前置任务
- 后续任务支持依赖多个前置任务
- 必须等所有前置任务都完成，后续任务才能开始
- 前置任务未完成时，后续任务仍然可见
- 首版不新增专门的“阻塞中”状态
- 用户尝试开始或完成后续任务时，如果前置任务未全部完成，系统直接提示

### 2.3 通知规则

- 当某条后续任务的所有前置任务全部完成时，需要通知该任务负责人
- 只有满足开始条件的那一刻通知一次，不重复骚扰

### 2.4 标签规则

- 每个任务都可以挂载多个标签
- 标签采用租户内共享标签库，同一租户下所有项目共用
- 标签通过独立管理维护，不在任务保存时自动创建
- 标签字段包含：`name`、`color`、`sort`
- 删除标签时，自动解除所有任务上的绑定关系
- 标签名称在同一租户内唯一

### 2.5 租户边界规则

- 项目需要显式保存 `tenantId`
- 任务通过所属项目继承租户边界，不单独新增 `projectTask.tenantId`
- 标签按项目所属租户校验，不允许跨租户挂载

### 2.6 范围边界

- 后续任务不是每条任务都必须有
- 首版不做自动生成后续任务
- 首版不做多级子任务
- 首版不做树形任务表、依赖图、甘特图

## 3. 目标与非目标

### 3.1 本次目标

- 支持为任务设置一级父子关系
- 支持为任务设置多个前置任务依赖
- 支持父任务在子任务全部完成后自动完成
- 支持依赖校验，阻止前置任务未完成的后续任务开始或完成
- 支持前置全部完成后通知后续任务负责人
- 支持为任务挂载多个标签
- 支持租户内共享标签库的后端管理能力
- 支持通过 `project.tenantId` 明确项目与任务的租户边界
- 输出稳定的后端接口与返回结构
- 为新增字段与接口补充 Swagger 注解

### 3.2 非目标

- 多级子任务
- 通用工作流引擎
- 自动生成后续任务
- 新增“阻塞中”状态
- 删除被依赖任务时自动迁移依赖关系
- 移动端布局适配

## 4. 方案对比

| 方案 | 说明 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 关系字段全部直接塞进 `projectTask` | 增加 `parentTaskId`，再把前置任务 ID 和标签 ID 以 JSON 或字符串形式塞进任务表 | 表少，落地快 | 依赖查询、循环校验、标签去重和后续扩展都不干净 | 不采用 |
| B. `projectTask` + 关系表 + 标签库表 | `projectTask` 负责真实任务；任务表增加 `parentTaskId`；依赖关系和标签关系单独建表维护；标签库按租户共享 | 结构清晰，满足当前需求，后续可平滑扩展 | 比方案 A 多几张表和一层服务逻辑 | 采用 |
| C. 通用工作流/流程引擎 + 元数据标签系统 | 抽象流程节点、边、规则、实例，再引入统一标签元数据中心 | 扩展性最强 | 范围明显过大，改动超出当前需求 | 不采用 |

最终采用方案 B。

## 5. 架构设计

### 5.1 模块归属

- 后端实现放在 `modelDesign/mod-project/mod-project-biz`
- 通知复用 `modelDesign/mod-system` 现有系统消息能力

这样做的原因：

- 子任务、后续任务和任务标签都属于项目任务领域本身，最适合继续沉淀在 `mod-project`
- 通知无需重复造轮子，直接接系统消息即可

### 5.2 关系模型

- 子任务关系：由任务表的 `parentTaskId` 表达
- 前置依赖关系：由独立关系表表达
- 任务标签关系：由标签库表和任务标签关系表表达

三者语义不同，不能混用：

- `parentTaskId` 表示归属关系
- 依赖关系表示开始条件
- 标签关系表示分类信息

一个任务可以同时具备这三种关系：

- 既是某个父任务下的子任务
- 同时又依赖若干前置任务
- 同时还挂载多个标签

### 5.3 租户边界

- `project` 新增 `tenantId` 作为项目租户归属
- `projectTask` 不单独保存 `tenantId`，统一通过 `projectId` 关联项目继承租户边界
- `taskTag` 直接保存 `tenantId`，表示该标签归属于哪个租户

这样设计的原因：

- 避免在任务表重复存储租户字段，减少冗余和一致性成本
- 让标签库可以按租户共享，而不绑定单个项目
- 让项目、任务、标签的租户校验都有明确落点

### 5.4 完成态判定

当前系统的任务状态是可配置的，且必须且只能有一个 `isCompleted = true` 的完成状态。

因此本次设计中所有“是否完成”的判断统一基于状态配置，而不是写死某个状态编码：

- 子任务是否完成：看其状态是否为当前配置的完成状态
- 父任务自动完成：更新为当前配置中的完成状态
- 前置任务是否完成：同样使用当前配置的完成态来判断

## 6. 数据模型设计

### 6.1 项目表 `project`

在现有表基础上新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `tenantId` | `bigint` | 所属租户 ID |

索引建议新增：

- `idx_project_tenantId`
- 如现有业务要求项目编号只在租户内唯一，则后续可将唯一约束由 `uk_project_code` 调整为 `(tenantId, code)`；本次先在设计中记录为需同步评估项

字段约束：

- `tenantId` 不允许为空
- 创建项目时由当前登录租户上下文注入，不通过请求体显式传入
- 编辑项目时不允许修改 `tenantId`

### 6.2 任务表 `projectTask`

在现有表基础上新增：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `parentTaskId` | `bigint` | 父任务 ID，空表示普通任务 |

索引建议新增：

- `idx_projectTask_parentTaskId`
- 如有需要，可补充 `(projectId, parentTaskId)` 组合索引，用于按父任务查询子任务

字段约束：

- `parentTaskId` 可为空
- 任务租户边界由 `projectId -> project.tenantId` 间接确定
- 子任务本身不允许继续作为其他任务的父任务，相关校验放在业务层

### 6.3 依赖关系表 `projectTaskDependency`

建议新增表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `bigserial` | 主键 |
| `taskId` | `bigint` | 当前任务 ID，也就是后续任务 |
| `predecessorTaskId` | `bigint` | 前置任务 ID |
| `createTime` | `timestamp` | 创建时间 |
| `updateTime` | `timestamp` | 更新时间 |

约束与索引建议：

- 唯一约束：`uk_projectTaskDependency_task_predecessor (taskId, predecessorTaskId)`
- 索引：`idx_projectTaskDependency_taskId`
- 索引：`idx_projectTaskDependency_predecessorTaskId`

说明：

- 不允许重复依赖
- `taskId` 与 `predecessorTaskId` 都指向真实任务
- 本次不做级联外键删除，由业务层显式校验和控制

### 6.4 标签库表 `taskTag`

建议新增表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `bigserial` | 主键 |
| `tenantId` | `bigint` | 所属租户 ID |
| `name` | `varchar(64)` | 标签名称 |
| `color` | `varchar(32)` | 标签颜色值 |
| `sort` | `integer` | 排序值 |
| `createTime` | `timestamp` | 创建时间 |
| `updateTime` | `timestamp` | 更新时间 |

约束与索引建议：

- 唯一约束：`uk_taskTag_tenant_name (tenantId, name)`
- 索引：`idx_taskTag_tenant_sort (tenantId, sort)`

说明：

- 标签名称在租户内唯一
- 标签不绑定单个项目，只绑定租户
- 首版不额外引入启停状态，删除即表示标签失效

### 6.5 任务标签关系表 `projectTaskTag`

建议新增表：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `bigserial` | 主键 |
| `taskId` | `bigint` | 任务 ID |
| `tagId` | `bigint` | 标签 ID |
| `createTime` | `timestamp` | 创建时间 |
| `updateTime` | `timestamp` | 更新时间 |

约束与索引建议：

- 唯一约束：`uk_projectTaskTag_task_tag (taskId, tagId)`
- 索引：`idx_projectTaskTag_taskId`
- 索引：`idx_projectTaskTag_tagId`

说明：

- 一个任务可以绑定多个标签
- 一个标签可以被多个任务复用
- 删除标签时，需要在同一事务内先删除 `projectTaskTag` 关系，再删除标签记录

## 7. 后端接口设计

### 7.1 项目接口调整

现有接口：

- `POST /project/create`
- `POST /project/edit`
- `GET /project/detail`
- `GET /project/list`

建议补充以下约定：

- 创建项目时，服务层从当前登录租户上下文写入 `tenantId`
- 编辑项目时，不暴露 `tenantId` 修改能力
- 项目列表和详情查询按当前登录租户隔离，只返回当前租户数据
- `ProjectDetailVo` 与列表结果建议补充 `tenantId` 只读字段，便于后续排障与服务间复用

### 7.2 任务创建与编辑接口扩展

现有接口：

- `POST /project/task/create`
- `POST /project/task/edit`

建议在请求对象中新增字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `parentTaskId` | `Long` | 父任务 ID，可空 |
| `predecessorTaskIds` | `List<Long>` | 前置任务 ID 列表，可空 |
| `tagIds` | `List<Long>` | 标签 ID 列表，可空 |

对应请求对象：

- `ProjectTaskCreateRequest`
- `ProjectTaskEditRequest`

都需要增加 Swagger 字段说明。

### 7.3 任务查询接口返回增强

建议在任务详情与任务列表返回对象中补充这些只读字段：

| 字段 | 说明 |
| --- | --- |
| `parentTaskId` | 父任务 ID |
| `parentTaskTitle` | 父任务标题 |
| `childTaskCount` | 子任务总数 |
| `completedChildTaskCount` | 已完成子任务数 |
| `predecessorTaskIds` | 前置任务 ID 列表 |
| `predecessorTasks` | 前置任务摘要列表 |
| `tagIds` | 标签 ID 列表 |
| `tags` | 标签摘要列表 |
| `canStart` | 是否允许开始 |
| `blockedReason` | 不能开始时的原因 |

前置任务摘要列表建议至少返回：

- `id`
- `title`
- `status`

标签摘要列表建议至少返回：

- `id`
- `name`
- `color`
- `sort`

说明：

- 即使当前阶段没有消费端改造，`canStart`、`blockedReason`、`tags` 也值得由后端直接返回
- 这样可以保证未来任何调用方都复用统一口径，而不是各自重复计算依赖是否满足或重复组装标签信息

### 7.4 标签管理接口

建议新增独立的标签管理控制器，例如：

- `GET /project/task/tag/list`
- `POST /project/task/tag/create`
- `POST /project/task/tag/edit`
- `POST /project/task/tag/deleted`

请求与返回约定：

- 创建标签：接收 `name`、`color`、`sort`
- 编辑标签：允许修改 `name`、`color`、`sort`
- 删除标签：支持批量删除，删除时自动解绑所有任务关系
- 列表接口按当前登录租户隔离，并按 `sort` 升序、`id` 升序返回

说明：

- 标签的租户边界由登录上下文注入，不通过请求体显式传入 `tenantId`

### 7.5 删除接口策略

任务删除：

- 现有 `POST /project/task/deleted` 建议增加删除前校验
- 如果该任务被其他任务作为前置任务依赖，则禁止删除
- 返回明确提示：请先解除后续任务依赖关系后再删除

标签删除：

- 删除标签时，允许自动解绑所有任务上的标签关系
- 删除逻辑应在同一事务内执行，避免出现标签已删但关系残留

首版仍不做自动解除任务依赖，避免产生用户不可感知的连锁副作用。

## 8. 核心业务规则

### 8.1 租户边界校验

- 创建项目时必须从当前登录租户上下文写入 `tenantId`
- 查询项目、任务、标签时，都只能访问当前租户数据
- 任务绑定标签时，必须校验任务所属项目的 `tenantId` 与标签的 `tenantId` 一致
- 前置任务、父任务、当前任务之间除了要求同项目外，也天然要求属于同一租户

### 8.2 子任务校验

- 父任务必须存在
- 父任务必须与当前任务属于同一项目
- 当前任务不能把自己设置为自己的父任务
- 子任务不能再拥有自己的子任务
- 不允许形成父子循环关系

### 8.3 前置依赖校验

- 前置任务必须存在
- 前置任务必须与当前任务属于同一项目
- 当前任务不能依赖自己
- 不允许重复依赖
- 不允许形成循环依赖

循环依赖需要检查直接和间接关系，例如：

- A 依赖 B
- B 依赖 C
- 则 C 不能再依赖 A

### 8.4 标签绑定校验

- 标签必须存在
- 标签必须属于当前任务所属项目的租户
- 同一任务不允许重复绑定同一标签
- 若请求中的 `tagIds` 为空列表，则表示清空当前任务标签
- 删除标签时，必须事务性删除对应 `projectTaskTag` 关系

### 8.5 状态推进校验

当任务存在未完成前置任务时，只允许停留在“起始待处理态”。

首版明确约定：

- 当前状态配置中按 `sort` 排序后的第一个非完成状态，视为“起始待处理态”
- 除“起始待处理态”之外的其他非完成状态，统一视为“推进态”
- 完成状态仍然单独按 `isCompleted = true` 判定

因此，无论是创建任务还是编辑任务，只要存在未完成前置任务：

- 允许保存为起始待处理态
- 不允许保存为执行中、待测试、待发布等推进态
- 不允许直接保存为完成态

如果任务存在未完成前置任务，则：

- 不允许进入推进态
- 不允许进入完成态
- 返回明确中文错误提示

### 8.6 父任务自动完成规则

触发时机：

- 某个子任务状态从未完成变为完成后

处理逻辑：

1. 查询同一个父任务下是否仍存在未完成子任务
2. 如果不存在，则将父任务自动更新为当前完成状态
3. 记录专门的自动完成变更日志

约束补充：

- 如果父任务本身已是完成状态，则不重复更新
- 如果父任务没有子任务，则不参与自动完成逻辑

### 8.7 负责人通知规则

触发时机：

- 某个前置任务从未完成变为完成

处理逻辑：

1. 查询所有依赖该任务的后续任务
2. 逐条重新判断这些后续任务的全部前置任务是否都已完成
3. 仅对“刚刚从不可开始变为可开始”的任务发送通知

通知前提：

- 后续任务有负责人
- 当前次状态变化确实让依赖条件满足

## 9. 通知与变更日志

### 9.1 系统消息

复用 `mod-system` 的系统消息能力，发送个人消息。

建议消息内容：

- 分类：`项目任务`
- 标题：`任务已满足开始条件`
- 内容：`任务《{任务标题}》依赖的前置任务已全部完成，请及时处理`
- 跳转地址：按现有系统消息协议预留任务定位地址，具体消费方式由调用方决定

### 9.2 变更日志

现有 `projectTaskChangeLog` 建议补充这些操作类型：

- `RELATION_UPDATE`
  - 父任务变化
  - 前置任务变化
- `TAG_BINDING_UPDATE`
  - 任务标签新增或移除
- `AUTO_COMPLETE`
  - 父任务因全部子任务完成而被系统自动完成
- `DEPENDENCY_READY`
  - 前置任务已全部完成，系统通知负责人

日志内容建议记录：

- 父任务由谁变成谁
- 前置任务新增了哪些、移除了哪些
- 标签新增了哪些、移除了哪些
- 自动完成的触发原因
- 依赖满足后已通知谁

这样用户后续查看任务历史时，能区分人工操作和系统自动行为。

## 10. 错误处理策略

后端返回的错误信息需要保持中文且可直接给最终用户阅读。

建议覆盖这些典型错误：

- 父任务不存在
- 前置任务不存在
- 标签不存在
- 项目不存在或不属于当前租户
- 任务标签与项目不属于同一租户
- 任务关系必须在同一项目内
- 任务不能依赖自己
- 任务关系形成循环依赖
- 子任务不能继续挂子任务
- 标签名称在当前租户内已存在
- 当前任务仍有未完成的前置任务，不能开始
- 当前任务仍有未完成的前置任务，不能完成
- 父任务仍有未完成子任务，不能手动完成
- 当前任务已被其他任务依赖，不能删除

## 12. 部署与发布影响

本次发布涉及：

- 数据库迁移
  - 给 `project` 增加 `tenantId`
  - 给 `projectTask` 增加 `parentTaskId`
  - 新增 `projectTaskDependency`
  - 新增 `taskTag`
  - 新增 `projectTaskTag`
- 后端接口字段扩展
- 历史项目数据回填 `tenantId`

迁移与回填说明：

1. `project.tenantId` 必须先完成字段增加和历史数据回填，再发布依赖租户隔离的新逻辑
2. 历史项目的 `tenantId` 回填来源需要以现有业务数据为准，优先采用项目创建人所属租户或现有租户归属表进行一次性回填
3. 如果历史项目无法可靠推导租户归属，本次发布前必须先人工确认回填策略，不能让 `tenantId` 留空上线

最小发布步骤建议：

1. 先执行数据库迁移脚本
2. 执行历史项目 `tenantId` 回填
3. 发布后端服务
4. 对项目列表、任务创建、标签管理和依赖通知做租户级冒烟检查

回滚思路：

- 后端可回滚到旧版本
- 若数据库已升级但代码回滚，`project.tenantId` 的非空约束与新增表结构需要提前评估旧版本是否兼容
- 如需完整回滚，优先保留新增表结构，仅回退业务代码，避免二次数据损坏

## 13. 实施范围结论

本次实现应聚焦以下交付闭环：

- 项目显式保存 `tenantId`，项目与任务查询按租户隔离
- 任务支持一级子任务
- 任务支持配置多个前置任务
- 父任务在子任务全部完成后自动完成
- 前置未全部完成时，后续任务不能开始或完成
- 前置全部完成后通知负责人
- 提供租户内共享标签库的后端管理能力
- 任务支持挂载多个标签
- 提供稳定的后端接口与返回字段

本次设计仅覆盖后端范围，不扩展到更重的流程引擎、树形任务管理和自动生成逻辑。
