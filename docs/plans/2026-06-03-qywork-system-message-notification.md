# 企业微信系统消息通知接入方案

## 1. 背景

当前项目已有系统消息发布与推送任务链路，也已有企业微信配置、
OAuth 绑定、access token 缓存和用户绑定关系。现需将系统消息通知接入
企业微信应用消息，使用户在收到站内系统消息时，也能通过企业微信接收通知。

参考文档：

- 企业微信“发送应用消息”：
  <https://developer.work.weixin.qq.com/document/path/90236>

## 2. 已确认边界

1. 接入现有系统消息通知链路，不新增独立消息来源。
2. 所有现有系统消息默认同步发送企业微信通知。
3. 企业微信接收人按现有用户企业微信绑定关系解析。
4. 未绑定企业微信的用户跳过企业微信推送，不阻断站内消息发布。
5. 企业微信消息类型使用应用消息接口的 `markdown` 类型。
6. 本方案只接入企业微信应用消息，不接入群机器人 Webhook。
7. 各个推送渠道必须封装为独立 provider，渠道之间不能互相影响。

## 3. 当前系统基础

### 3.1 系统消息链路

当前后端已有以下基础能力：

- `SystemMessageApi`：业务模块发布系统消息的统一入口。
- `SystemMessagePublishService`：负责保存系统消息和创建推送任务。
- `SystemMessagePushTask`：记录第三方推送任务状态、重试次数和错误信息。
- `SystemMessagePushAdapter`：第三方推送适配器接口。
- `SystemMessagePushAdapterRegistry`：统一管理可用推送适配器。
- `SystemMessagePushProducer` / `SystemMessagePushConsumer`：通过 Kafka
  投递并消费系统消息推送任务。

### 3.2 企业微信链路

当前后端已有以下基础能力：

- `QyworkCorpConfigService`：读取租户企业微信配置。
- `QyworkAccessTokenService`：获取并缓存企业微信 access token。
- `UserOauthService`：读取用户第三方账号绑定关系。
- `UserOauth`：保存用户企业微信 `providerUserId`，可作为企业微信
  应用消息的 `touser`。

## 4. 目标方案

### 4.1 默认推送策略

系统消息发布时，默认增加企业微信推送适配器编码。这样现有业务调用方不需要
逐个补 `adapterCodes`，即可让已有系统消息同步进入企业微信推送任务。

如果后续需要让某些消息只保留站内通知，可再扩展显式禁用企业微信通道的配置。
第一版不引入额外禁用策略，避免扩大接口和调用方改造范围。

### 4.2 推送渠道 Provider 设计

各个推送渠道需要封装为独立 provider。provider 是系统消息第三方推送能力的
业务边界，用于隔离不同通知渠道的配置、接收人解析、消息体组装、发送客户端、
异常处理和日志记录。

第一版可复用现有 `SystemMessagePushAdapter` 作为 provider 接口，或在其上方
增加更语义化的 provider 命名封装；关键约束是渠道实现之间不能共享可变状态，
也不能让一个渠道的失败影响其它渠道。

provider 隔离规则：

- 每个渠道独立解析接收人，企业微信只处理企业微信绑定关系。
- 每个渠道独立组装消息体，不复用其它渠道的格式化结果。
- 每个渠道独立调用发送客户端，不在 provider 之间互相调用。
- 每个渠道独立产生推送任务，避免一个渠道失败阻断其它渠道任务创建。
- 每个渠道异常只影响当前渠道的推送任务状态和重试，不影响站内消息和其它渠道。
- provider 注册表只负责查找和调度 provider，不承载具体渠道业务逻辑。

### 4.3 企业微信 Provider

新增企业微信系统消息推送 provider，实现或包装 `SystemMessagePushAdapter`：

- provider 编码建议为 `qywork`。
- 从 `SystemMessagePushContext` 读取租户、接收用户、标题、正文和跳转地址。
- 按租户与用户 ID 查询企业微信有效绑定。
- 未查询到有效绑定时直接跳过，不抛出业务异常。
- 查询到绑定后，通过企业微信应用消息接口发送 `markdown` 消息。
- 企业微信接口失败时抛出异常，由现有推送任务重试与死信机制承接。
- 企业微信 provider 不得直接影响其它 provider 的推送任务、配置和状态。

### 4.4 Markdown 消息内容

企业微信 `markdown` 内容建议由以下信息组成：

```markdown
# {消息标题}

{消息正文}

[查看详情]({跳转地址})
```

处理规则：

- 标题为空的情况不会出现，因为系统消息发布入口已有标题必填校验。
- 正文为空的情况不会出现，因为系统消息发布入口已有正文必填校验。
- 跳转地址为空时，不输出“查看详情”链接。
- 对 Markdown 特殊字符做必要转义或清洗，避免用户输入破坏消息结构。
- 控制最终内容长度，超出企业微信限制时截断正文并保留标题。

### 4.5 企业微信客户端

新增企业微信应用消息客户端，负责调用：

```text
POST /cgi-bin/message/send?access_token={accessToken}
```

请求体使用企业微信 `markdown` 应用消息结构，核心字段包括：

- `touser`：企业微信成员 ID，即绑定表中的 `providerUserId`。
- `msgtype`：固定为 `markdown`。
- `agentid`：租户企业微信应用 ID。
- `markdown.content`：由系统消息标题、正文和跳转地址组装。

客户端需要校验企业微信返回：

- `errcode = 0`：发送成功。
- `errcode != 0`：按网关失败处理，抛出异常并保留 `errmsg`。
- 返回中如包含无效用户字段，应记录到错误信息，便于排查绑定失效。

### 4.6 配置复用

企业微信消息发送复用现有租户企业微信配置：

- `corpId`
- `corpSecret`
- `agentId`

不新增独立消息发送密钥。这样 OAuth 绑定和应用消息发送使用同一套租户企业微信
应用配置，减少配置漂移。

## 5. 失败处理

### 5.1 未绑定企业微信

未绑定用户不创建额外错误，不影响站内消息。适配器可直接返回，推送任务标记为
成功或跳过状态，具体以现有 `SystemMessagePushConsumer` 的成功语义为准。

### 5.2 企业微信配置缺失

租户未配置企业微信或配置不可用时，企业微信推送失败应进入现有重试链路。
这类问题属于配置错误，不能静默吞掉，否则会掩盖真实接入问题。

### 5.3 access token 获取失败

access token 获取失败时，适配器抛出异常，由现有推送任务重试机制处理。

### 5.4 企业微信接口返回失败

企业微信接口返回非成功 `errcode` 时，记录 `errcode`、`errmsg` 和接收人信息，
并抛出异常交给现有重试机制。该异常只影响企业微信 provider 对应的推送任务，
不能回滚站内消息，也不能影响其它 provider 的推送任务。

## 6. 数据库影响

本方案优先复用现有系统消息推送任务表和第三方账号绑定表。

预计不新增数据库表和字段。如果实施中发现现有推送任务状态无法表达“未绑定跳过”，
优先复用成功状态并在日志中说明跳过原因；只有确实影响后续排障或统计时，再新增
更高版本号迁移文件扩展状态或备注字段。

## 7. 接口影响

对外业务接口默认不变：

- 业务模块仍通过 `SystemMessageApi.publish(...)` 发布消息。
- 前端消息中心接口不变。
- 企业微信绑定接口不变。

内部行为变化：

- 系统消息发布后会默认额外创建企业微信推送任务。
- 已绑定企业微信的用户会收到企业微信应用消息。
- 各推送渠道通过 provider 独立执行，某个渠道失败不会影响其它渠道。

## 8. 测试范围

### 8.1 单元测试

建议补充以下测试：

1. `SystemMessagePublishService` 默认补入 `qywork` 适配器。
2. 显式传入适配器编码时，企业微信适配器不重复创建。
3. 企业微信适配器在用户未绑定时跳过发送。
4. 企业微信适配器在用户已绑定时调用消息发送客户端。
5. 企业微信消息客户端成功解析 `errcode = 0`。
6. 企业微信消息客户端在非 0 `errcode` 时抛出异常。
7. Markdown 内容组装覆盖有跳转地址和无跳转地址两种场景。
8. 多 provider 场景下，企业微信 provider 失败不影响其它 provider 任务。

### 8.2 后端验证命令

后端单测按 boot 聚合入口运行，例如：

```bash
./mvnw -pl boot -am -Dtest=SystemMessagePublishServiceTest,QyworkSystemMessagePushAdapterTest \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

如目标测试通过但 reactor 后续其它模块测试编译失败，应按项目经验区分目标验证结果
和仓库既有问题。

## 9. 回滚策略

如接入后需要快速回滚：

1. 从默认适配器列表中移除 `qywork`。
2. 保留企业微信客户端和适配器代码，不再默认触发。
3. 如仍需彻底回滚，再删除适配器 Bean 或通过配置关闭。

该回滚方式不会影响站内系统消息保存和前端消息中心读取。
